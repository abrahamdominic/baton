# Internationalization

How Baton's translation system works, and how to extend it.

## Where translation files live

```text
/locales
  /en/<namespace>.json     # reference locale, always complete
  /es/<namespace>.json
```

One file per namespace (`common`, `navigation`, `auth`, `dashboard`, `repos`,
`pulls`, `billing`, `teams`, `organizations`, `messaging`, `notifications`,
`settings`, `language`, `theme`, `admin`, `errors`, `onboarding`, `legal`).
Namespaces are logical areas, not one file per page, so a string is defined once
and reused.

Keys are namespaced with a colon at the call site and flattened with a dot
internally:

```text
locales/en/dashboard.json   { "waiting_on_you": "Waiting on you" }
t("dashboard:waiting_on_you")
```

## How to add a new translation key

1. Add it to `locales/en/<namespace>.json`.
2. Add it to **every** other locale, or `npm run i18n:check` fails.
3. Use it: `t("namespace:key")` or `tc("namespace:key", count)`.

## How to add a new language

1. Add the locale to `SUPPORTED_LOCALES` in `src/lib/i18n/config.ts`.
2. Add a loader entry in `src/lib/i18n/bundles.ts`.
3. Copy `locales/en/*.json` to `locales/<code>/` and translate the values.
4. Run `npm run i18n:check` until it reports zero errors.
5. Add tests to `src/lib/i18n/i18n.test.ts` for anything locale-specific.
6. If the language is right-to-left, add it to `RTL_LOCALES` in
   `src/lib/i18n/config.ts`. The `dir` attribute, the prepaint script, and
   `directionFor` all read from that one set.

No component changes are needed at any step. That is the point: a component
references a key, and a key's meaning comes from the resource files.

## How locale detection works

Resolution runs on the server for the first paint, then on the client for
interactions.

**Server** (`src/lib/i18n/resolve.ts`), highest precedence first:

1. `baton.locale` cookie — set when the user picks a language on any device
2. the signed-in account's `User.preferredLanguage`
3. the `Accept-Language` header
4. English

**Client** (`src/lib/i18n/provider.tsx`):

1. the account preference, when present
2. a local `baton.language` value the user explicitly chose on this device
3. the browser's language
4. English

`resolveLocale` handles regional variants: `es-MX` and `es-419` both fall back to
`es`, and an unsupported tag falls back to English. It also parses full
`Accept-Language` headers, so `fr-CA,fr;q=0.9,en;q=0.8` resolves to a supported
locale rather than being treated as one literal tag.

A **stale local value never overrides a newer account value**: the local value
is only allowed to win sign-in if it was an explicit user choice, not passive
browser detection. `readStoredLocale` records which of the two it was.

## How user preferences are persisted

Two levels, as required:

- **Account** — `User.preferredLanguage` (nullable `String`, migration
  `0007_user_preferred_language`). Nullable with no default on purpose: `null`
  means "never chose", which is distinct from "chose English" and is what lets
  browser detection run for a new visitor.
- **Local** — `localStorage["baton.language"]`, written on every change so a
  refresh keeps the choice with no network round trip.

On save, the order is: update React state → write `localStorage` → write the
cookie → write the database. The UI never blocks on the database, and if the
database write fails the language stays changed locally and the user is told
once, in the page's own language.

`savePreferredLanguageAction` reads the user id from the session, never from the
client, so one user cannot rewrite another's preference.

## Why there is no `/{locale}/...` route

A locale-prefixed path was considered and rejected. lan.md requires that a
language change cause no redirect and no route change, so the language has to be
request state rather than URL state. Keeping it in a cookie and a header means
switching languages re-renders React without touching the router, and it leaves
every existing route and deep link untouched.

## How RTL support works

`directionFor(locale)` returns `rtl` for languages listed in `RTL_LOCALES`. It is
applied in three places that must agree:

- `<html dir>` is rendered on the server, so the first paint is already correct
- the pre-paint script in `<head>` re-stamps `lang` and `dir` before hydration
- the provider keeps both in sync on every change

Styling uses logical properties (`ps-*`, `pe-*`, `ms-*`, `me-*`, `start-*`,
`end-*`) rather than `left`/`right`, so a direction flip does not need a second
stylesheet. Directional icons must mirror themselves; a back arrow is
meaningless pointing the wrong way.

## How to test translations

```bash
npm run typecheck
npm run lint
npm test                 # unit + database-backed projects
npm run i18n:check       # missing / unused / placeholder / structure
npm run build
```

`npm run i18n:check` is the one that catches translation problems specifically.
It fails on a missing key, an extra key with no English source, an empty value,
a malformed namespace, and a placeholder mismatch — for example English
`"{{count}} files changed"` against Spanish `"archivos modificados"`, which would
otherwise ship a literal `{{count}}` to a user. Unused keys are reported as
warnings, since a key can legitimately be referenced dynamically.

## Interpolation and pluralization

Never build a string in a component:

```tsx
// Wrong
<p>{`Welcome, ${user.name}`}</p>

// Right
<p>{t("dashboard:greeting", { name: user.name })}</p>
```

```json
{ "greeting": "Welcome back, {{name}}" }
```

A `{{placeholder}}` with no supplied value **throws in development** and is left
visible in production, so the test suite catches the mistake rather than a user.

Plurals use the count-aware form and are stored with CLDR category suffixes:

```json
{
  "checks_passed": {
    "one": "{{count}} check passed",
    "other": "{{count}} checks passed"
  }
}
```

```tsx
tc("pulls:checks_passed", checks.length)
```

Categories go through `Intl.PluralRules`, so this is genuinely locale-aware
rather than `count === 1 ? a : b`. Arabic resolves `0`/`1`/`2`/`3–10` to
`zero`/`one`/`two`/`few`, and Russian resolves `0`/`5` to `many`. A locale that
has not defined a category falls back to `other`, then `one`.

## Dates, numbers, and currency

Use the formatters on the context rather than calling `Intl` inline, so the
active locale is always the one used:

```tsx
const { formatNumber, formatDate, formatCurrency } = useI18n();

formatNumber(count);                    // 1,000 in en · 1.000 in de
formatDate(date);                       // locale-appropriate
formatCurrency(cents, "USD");           // $15.00
```

Values that must not be localized — repository names, URLs, commit hashes, API
keys, code — are deliberately rendered verbatim.

## Missing translations

A key that exists in English but not in the active locale falls back to English.
A key that exists in no locale returns the key itself, which is visible in
development without crashing. A bundle that fails to load resolves to English
alone. There is no path where a missing translation takes down a page.

## Flags

The picker shows a language **code badge** (`ES`, `EN`) rather than a flag,
alongside the native name. A flag would imply a country, and Spanish is not
Spanish-dad's-flag — Spanish is spoken across many countries, and so is
everything else in the list. The code is what actually identifies a language.
